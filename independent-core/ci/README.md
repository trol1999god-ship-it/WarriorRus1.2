# План запуска Android QA

## Локальный изолированный запуск (28 октября)

Добавлен `run_local_emulator.py`: он создаёт новый временный AVD, запускает adb и эмулятор в одном контексте и ждёт настоящего `sys.boot_completed=1`. Это важно для сред, где отдельные команды исполняются в разных сетевых пространствах. Готовые APK передаются через `--app` и `--tests`; их SHA256 записываются в `local-run.json`. Нужны одинаковые одноразовые подписи тестового приложения и инструментации.

SDK должен содержать `emulator`, `platform-tools` и `system-images/android-23/default/x86` (либо `android-35/default/x86_64` для API35). Пример после подготовки APK:

```
python3 ci/run_local_emulator.py --sdk /path/sdk --app /path/qa/app.apk --tests /path/qa/tests.apk --api 23 --output /path/new-results
```

По умолчанию выполняются все 19 сценариев. `--modes coordinates catalogscreen geometryedit` выбирает конкретные сценарии, не отмечая остальные пройденными. При первом отказе драйвер завершается с ошибкой. Таймаут загрузки настраивается через `--boot-timeout`; отсутствие загрузки не подменяется успешным результатом. Используется программная эмуляция без KVM. Логи и свойства Android сохраняются, временный AVD удаляется, отдельные группы процессов adb/эмулятора останавливаются. Личная установка 26.1 и её ключ не используются.

Фактические результаты запусков фиксируются отдельно от этого описания. Наличие скрипта и успешная компиляция не означают успешного исполнения сценариев.

## Конкретное предлагаемое размещение

После отдельного разрешения на публикацию текущих исходников:

1. В `trol1999god-ship-it/WarriorRus1.2` создать одну ветку `independent-core-qa` и черновой PR. Содержимое этого проекта разместить в `independent-core/`; шаблон `ci/independent-core-qa.yml` — в `.github/workflows/independent-core-qa.yml`.
2. Текущие файлы старого приложения не заменять, PR автоматически не сливать. Подпись/идентификатор установленной 26.1 этим действием не меняются.
3. Workflow запускает JVM-проверки, компиляцию API23, проверку замыкания собственных классов и инструментацию на одноразовых Android API23/x86 и API35/x86_64 с KVM.
4. Проверяются binary, independence, offlineformats, cachewrites, cacheexport, launcher, coordinates, catalogscreen, geometryedit. Каждый независимый сценарий получает очищенные данные только тестового пакета на эмуляторе.
5. В артефакты попадают результаты и синтетические тестовые файлы. APK и временный ключ подписи туда не включаются. Это не пользовательский выпуск и не полная приёмка всех возможностей 26.1.

Репозиторий публичный: размещённые собственные исходники и упакованная графика будут доступны всем. Поэтому подготовка сделана локально; размещение текущего отдельного APK-проекта в старом публичном репозитории без уточнения не выполнено. В архиве нет личных проектов, настоящих ключей подписи, паролей, исходного APK 26.1 или пользовательского кеша.

## Локальная подготовка

`build_android_qa.py` проверяет SHA256 R8 8.3.37 и apktool 2.11.1, использует android.jar API23/aapt2 из SDK, собирает своё приложение и тесты и подписывает оба одноразовым ключом. Для запуска требуются готовые `platforms;android-23` и `build-tools;35.0.0`. Текущая локальная smoke-проверка использует имеющиеся инструменты из рабочей среды; загрузка этих зависимостей в GitHub отдельно не проверена.

`run_android_checks.py` откажется очищать данные при серийном номере физического устройства, при отсутствии свойства qemu или незавершённой загрузке ОС. При ненулевом результате команды либо отсутствии ожидаемого PASS сценарий считается неуспешным. `sys.boot_completed` не подменяется.

Зависимости/схема action сверены с исходным action.yml: https://github.com/ReactiveCircus/android-emulator-runner/blob/main/action.yml . Публикация этого плана не выполнена.

`--install-timeout 240 --no-streaming` доступны в локальном запускателе и драйвере для диагностики медленной установки. Они не отменяют проверки результата и не делают неуспешный сценарий успешным. В более раннем прогоне API23 прошёл девять сценариев; API35 остановился на недоступном хранилище и не принят. Workflow в GitHub не публиковался.

## Пара проверки вершин на карте

На предыдущем этапе редактора вершин набор состоял из 11 сценариев. Добавленная тогда пара — `geometrymap geometrymapreopen`; второй сценарий допустим только сразу после первого в том же запуске. Драйвер делает force-stop между ними и сохраняет синтетические данные первого. В текущем наборе второе исключение — objectmanagerreopen; перед остальными сценариями очистка пакета обязательна. Так проверяется восстановление черновика после остановки процесса. Пара также проверяет перемещение/масштаб карты, не затрагивая координаты фигуры.

Java 8 сигнатуры java.lang.invoke используются при компиляции тестов против API23 только как ABI-заглушки. Они компилируются отдельно, не входят в jar классов инструментации, а D8 десахаризует лямбды для min-api23.

## Менеджер объектов

Полный набор теперь включает `objectmanager` и непосредственно следующий `objectmanagerreopen`. Второй режим требует успешного первого в том же запуске; только для этой пары и пары geometrymap процесс останавливается без pm clear перед восстановлением. Остальные режимы начинают с очищенных синтетических данных. `objectmanager` также проверяет два конкурентных менеджера с одним токеном и преобразование прямого KML Feature в Document на явной записи.

Локальный запускатель принудительно работает без ускорения и задаёт `ANDROID_I_WANT_MY_TCG=yes`, необходимое новым эмуляторам для такого режима. Отсутствие/невозможность запуска adb записывается как ошибка; запуск с ошибкой не считается Android-проверкой.

Итог предыдущего этапа менеджера: 13/13 сценариев API23, 962 утверждения; JVM 80 449. Android15/16 и физическое устройство не приняты. Это не полная приёмка 26.1.

## Внутренний буфер

Добавлены `clipboard` и непосредственно следующий `clipboardreopen`. Второй режим требует первого в том же запуске. Синтетические данные сохраняются только для пар geometrymap/geometrymapreopen, objectmanager/objectmanagerreopen и clipboard/clipboardreopen; каждый первый режим пары и все одиночные режимы выполняют pm clear. Настоящий force-stop между фазами обязателен. При первом отказе запуск прекращается.

Сценарий clipboard включает отказ при ошибке записи payloads, откат уже записанных payloads при отказе расходования вырезанного выбора, отказ при замене буфера после подтверждения и при несовпадении проекта, повреждение/очистку буфера, действия UI и неизменность синтетического системного буфера. На Android6 его тестовая инициализация выполняется в главном потоке. Production-менеджер к системному ClipboardManager не обращается.

Исторический итог этапа буфера: 15/15 сценариев API23, 1081 утверждение (clipboard 84, clipboardreopen 25); JVM 80 504. Полная приёмка замены не установлена. Доказательства — `security/object-clipboard-qa-2026-10-28/`.

## Список менеджера

Добавлены `managerfilters` и непосредственно следующий `managerfiltersreopen`. Данные между ними сохраняются после настоящего force-stop; первый режим пары по-прежнему начинается с pm clear. Это четвёртая пара восстановления наряду с geometrymap, objectmanager и clipboard. У сценариев есть проверки исходных адресов после фильтра/сортировки, скрытого выбора, реальных операций, сохранности payloads и восстановления параметров с очищенным выбором. Формы меняются через реальные виджеты на главном потоке; это не приёмка всех жестов/устройств.

Исторический итог списка менеджера: 17/17 сценариев API23, 1171 утверждение (managerfilters 69, managerfiltersreopen 14); JVM 80 572. Доказательства — `security/object-listing-qa-2026-10-28/`. Это не полная приёмка замены 26.1.

## Массовая видимость

Добавлены `managervisibility` и непосредственно следующий `managervisibilityreopen`. Второй режим сохраняет синтетическую БД после настоящего force-stop. Первый режим пары и все одиночные режимы делают pm clear. Это пятая пара восстановления. Проверяются реальный KmlProject.visible/features, imported false/true, UI-предпросмотр/отмена, изменение папки и ребёнка, отсутствие изменения собственных флагов невыбранных детей, обновление карты при возврате, отказ устаревшей записи и откат после внедрённой ошибки SQLite. Нулевая команда проверяется при запретительном триггере и не пишет payloads.

Финальный итог массовой видимости: 19/19 сценариев API23, 1262 утверждения (managervisibility 72, reopen 15); JVM 80 628. Журналы и суммы — `security/object-visibility-qa-2026-10-28/`. Тестовый click после первого отказа обновляет accessibility-узел и ждёт visible/enabled; не повторяет успешно принятые действия, при отказе сохраняет снимок. Полный набор пройден заново на прежнем production APK с обновлённой инструментацией.

Поиск по описаниям: API23/x86: 19/19 сценариев, 1288 утверждений; managerfilters 94, force-stop reopen 15. JVM — 80 660, собственных классов — 373. Все сценарии выполнены на одном production APK. Расширенная пара managerfilters / managerfiltersreopen проверяет HTML-текст, область поиска, отмену/сброс и восстановление поля/запроса после force-stop. Результаты — `security/object-description-search-qa-2026-10-28/`.

Собственные даты KML: API23/x86: 21/21 сценариев, 1391 утверждений; managerdates 79, force-stop reopen 15. JVM — 80 760, собственных классов — 382. Все прежние 19 сценариев повторены на одном и том же production APK. Новая шестая пара managerdates / managerdatesreopen проверяет диапазоны/UTC/частичную точность, ошибки/отмену, отсутствие и нераспознанность, комбинации и настоящий перенос, сохранность метаданных/буфера/вложения и force-stop. По умолчанию драйвер запускает все 21 сценарий; reopen требует предшествующего успешного первого режима. Журналы — `security/object-date-search-qa-2026-10-28/`.
